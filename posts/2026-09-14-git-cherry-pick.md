브랜치 전체를 합칠 필요 없이 특정 커밋 하나만 다른 브랜치로 옮기고 싶을 때가 있다. 예를 들어 개발 브랜치에서 급한 버그를 고쳤는데, 그 수정만 배포 브랜치에도 반영해야 하는 상황이다. 이럴 때 `git merge`는 너무 많은 것을 끌고 오고, `git cherry-pick`은 딱 필요한 만큼만 가져온다.

## cherry-pick의 기본 동작

cherry-pick은 지정한 커밋이 만든 변경 사항(diff)을 계산해서, 현재 체크아웃된 브랜치 위에 새로운 커밋으로 다시 적용한다. 원본 커밋을 이동시키는 게 아니라 복사하는 것이므로, 같은 변경 내용을 담은 커밋이 해시만 다르게 두 브랜치에 각각 존재하게 된다.

```
git checkout release
git cherry-pick a1b2c3d
```

여러 커밋을 순서대로 가져오고 싶다면 해시를 나열하거나 범위를 지정할 수 있다.

```
git cherry-pick a1b2c3d..f4e5d6c
```

## 충돌이 나면

원본 커밋이 만들어진 브랜치와 현재 브랜치의 코드가 다르면 충돌이 날 수 있다. 이때는 merge 충돌과 똑같이 파일을 열어 직접 해결한 뒤 `git add`로 표시하고, `git cherry-pick --continue`로 이어간다. 그만두고 싶다면 `git cherry-pick --abort`로 원래 상태로 되돌릴 수 있다.

## 언제 조심해야 할까

cherry-pick으로 만들어진 커밋은 원본과 내용은 같지만 해시가 다른 별개의 커밋이다. 나중에 두 브랜치를 merge하면 Git이 이미 같은 변경이 반영됐다는 걸 알아채고 대체로 문제없이 넘어가지만, 커밋 이력만 보면 같은 수정이 두 번 있는 것처럼 보여 혼란스러울 수 있다. 그래서 핫픽스처럼 예외적인 경우에만 쓰고, 평소 브랜치를 합칠 때는 merge나 rebase를 쓰는 편이 이력을 더 깔끔하게 유지한다.

정리하면, cherry-pick은 브랜치 전체가 아니라 커밋 단위로 변경 사항을 옮기고 싶을 때 쓰는 도구다. 원본을 복사해 새 커밋을 만든다는 점을 기억하면 충돌 해결이나 이후 merge에서 헷갈릴 일이 줄어든다.
