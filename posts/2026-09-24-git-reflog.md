`git reset --hard`를 잘못 실행하거나 브랜치를 지웠다가 작업 내역이 통째로 사라진 줄 알고 식은땀을 흘린 적이 있다. 사실 Git은 커밋을 그렇게 쉽게 버리지 않는다. `git reflog`를 쓰면 HEAD가 지금까지 가리켰던 위치의 기록을 그대로 볼 수 있어서, 실수로 놓친 커밋도 대부분 되찾을 수 있다.

## reflog가 기록하는 것

reflog는 커밋 그래프가 아니라 로컬 저장소에서 HEAD와 브랜치 포인터가 움직인 이력을 시간순으로 남긴다. `checkout`, `commit`, `merge`, `rebase`, `reset` 같은 명령을 실행할 때마다 한 줄씩 쌓이며, `git log`에서는 더 이상 보이지 않는 커밋이라도 한동안 여기에는 남아 있다.

```
git reflog
```

`a1b2c3d HEAD@{0}: reset: moving to HEAD~3` 같은 줄을 보면, 몇 번째 이동에서 어떤 명령으로 어디로 옮겨갔는지 알 수 있다.

## 잃어버린 커밋 되돌리기

원하는 시점의 해시를 찾았다면 그 지점으로 새 브랜치를 만들거나 현재 브랜치를 되돌리면 된다.

```
git branch recovered-work HEAD@{2}
git reset --hard HEAD@{2}
```

새 브랜치로 받아두면 기존 브랜치를 건드리지 않고 안전하게 내용을 확인할 수 있어서, 확실하지 않을 땐 이쪽을 먼저 시도하는 편이 낫다.

## 영원히 남는 건 아니다

reflog 항목은 기본적으로 90일이 지나면 가비지 컬렉션 대상이 되고, 연결이 끊긴 커밋은 결국 저장소에서 삭제된다. 즉 reflog는 실수를 되돌릴 여유 시간을 벌어주는 안전망이지, 영구 백업은 아니다. 중요한 작업은 결국 원격 저장소에 push하거나 브랜치로 남겨두는 게 안전하다.

정리하면, reflog는 원격에 올리지 않은 로컬 커밋이 눈앞에서 사라진 것처럼 보일 때 가장 먼저 확인해야 할 도구다. HEAD가 거쳐온 위치를 그대로 기록해두기 때문에, 잘못된 reset이나 rebase도 대부분 되돌릴 수 있다는 걸 기억해두면 당황하지 않고 대처할 수 있다.
