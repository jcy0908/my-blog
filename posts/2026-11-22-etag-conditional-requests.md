`Cache-Control`로 캐시 유효 기간을 정해도, 기간이 지나면 브라우저는 파일 전체를 다시 받아야 할까? 내용이 하나도 안 바뀌었는데도 똑같은 CSS 파일을 통째로 다시 내려받는 건 아깝다. HTTP에는 "바뀐 게 있으면 그때만 새로 보내달라"고 물어보는 조건부 요청이라는 방법이 있다는 걸 오늘 정리했다.

## ETag, 콘텐츠의 지문

서버는 응답에 `ETag` 헤더로 리소스 내용에 대한 해시값 같은 식별자를 붙여줄 수 있다. 내용이 1비트라도 바뀌면 이 값도 달라진다.

```
ETag: "a1b2c3d4"
```

브라우저는 이 값을 캐시에 저장해두고, 다음에 같은 리소스를 요청할 때 함께 들고 간다.

## If-None-Match로 물어보기

캐시 기간이 지나 다시 요청해야 할 때, 브라우저는 저장해둔 ETag를 `If-None-Match` 헤더에 담아 보낸다. "내가 가진 버전이 이거 맞아?"라고 묻는 셈이다.

```
GET /style.css
If-None-Match: "a1b2c3d4"
```

## 304 Not Modified

서버는 현재 리소스의 ETag와 요청에 담긴 값을 비교한다. 같으면 바뀐 게 없다는 뜻이므로, 본문 없이 `304 Not Modified` 상태 코드만 돌려준다. 다르면 새 리소스와 새 ETag를 담아 평소처럼 `200 OK`로 응답한다. 304 응답은 본문이 없어 전송량이 훨씬 적고, 브라우저는 캐시에 있던 버전을 그대로 재사용한다.

## Last-Modified와의 차이

비슷한 역할을 하는 `Last-Modified`/`If-Modified-Since` 헤더도 있는데, 이건 수정 시각(초 단위)만 비교한다. 내용이 같아도 타임스탬프만 바뀌면 다시 받게 될 수 있어 ETag보다 정확도가 떨어진다. 둘 다 있으면 서버는 보통 ETag를 우선한다.

## 요약

ETag와 `If-None-Match`를 이용한 조건부 요청은 캐시가 만료된 뒤에도 내용이 실제로 바뀌었는지 가볍게 확인하는 장치다. 바뀌지 않았다면 서버는 본문 없는 304 응답만 보내 불필요한 전송을 막고, 바뀌었다면 새 콘텐츠와 새 ETag로 캐시를 갱신시킨다.
