며칠 전엔 잘 되던 기능이 지금은 깨져 있는데, 그 사이 커밋이 수십 개라면 하나씩 되돌려보기엔 너무 번거롭다. 오늘은 이럴 때 쓰는 `git bisect`를 배웠다. 이진 탐색으로 버그가 처음 생긴 커밋을 빠르게 찾아주는 도구다.

## 이진 탐색으로 범위 좁히기

`git bisect start` 로 시작한 뒤, 지금 상태를 `git bisect bad`, 정상이었던 과거 커밋을 `git bisect good <커밋>` 으로 지정한다. 그러면 두 지점 사이 중간 커밋으로 자동 체크아웃되고, 커밋이 N개면 확인은 log2(N)번이면 충분하다.

## 매 단계 직접 판정하기

체크아웃된 커밋에서 버그를 재현해보고 있으면 `bad`, 없으면 `good` 을 입력한다. 반복할수록 범위가 좁혀지다가 마지막엔 문제의 첫 커밋을 알려준다. 끝나면 `git bisect reset` 으로 원래 브랜치로 돌아온다.

## 스크립트로 자동화하기

판정을 스크립트로 표현할 수 있다면 `git bisect run <스크립트>` 한 줄로 전체 과정을 자동화할 수 있다. 종료 코드가 0이면 good, 아니면 bad로 자동 판정되어 사람이 매번 확인할 필요가 없다.

```
git bisect start
git bisect bad
git bisect good v1.2.0
git bisect run npm test
```

감으로 커밋 로그를 뒤지는 대신 git bisect로 이진 탐색을 하면 훨씬 빠르고 정확하게 원인 커밋을 찾을 수 있다는 걸 배웠다.
