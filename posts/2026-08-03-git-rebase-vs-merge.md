브랜치를 합칠 때마다 `merge`와 `rebase` 중 뭘 써야 할지 헷갈렸는데, 오늘 커밋 히스토리 관점에서 둘의 차이를 정리해봤다.

## merge: 있는 그대로 합치기

`git merge`는 두 브랜치의 변경 이력을 그대로 두고, 두 부모를 가리키는 **병합 커밋**을 하나 새로 만든다. 누가 언제 브랜치를 나눴다가 합쳤는지가 히스토리에 그대로 남기 때문에 추적성은 좋지만, 브랜치가 많아지면 로그가 지저분해진다.

## rebase: 이력을 다시 쓰기

`git rebase`는 내 커밋들을 떼어냈다가 대상 브랜치 끝에 다시 이어 붙인다. 그 결과 병합 커밋 없이 한 줄로 쭉 이어지는 깔끔한 히스토리가 만들어진다. 다만 커밋의 해시가 전부 바뀌므로, 이미 원격에 push해서 다른 사람이 받아간 브랜치를 rebase하면 충돌의 원인이 된다.

```
# 예시: 로컬 작업 브랜치를 최신 main 위로 재배치
git fetch origin
git rebase origin/main
```

## 실전 기준

혼자 작업 중인 로컬 브랜치는 `rebase`로 깔끔하게 정리하고, 이미 공유된 브랜치나 PR이 열린 브랜치는 `merge`로 합치는 편이 안전하다는 걸 다시 확인했다.

정리하면, rebase는 "히스토리를 예쁘게", merge는 "사실을 그대로" 남기는 방식이라는 관점 차이가 선택 기준이 된다.
