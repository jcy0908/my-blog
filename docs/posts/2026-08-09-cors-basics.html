CORS, 브라우저가 API 요청을 막는 이유

2026년 8월 9일

  • 브라우저
  • 네트워크
  • 보안

오늘 로컬에서 다른 포트에 떠 있는 API 서버를 호출하다가 콘솔에 시뻘건 CORS 에러를 봤다. 그동안은 "서버에서 헤더만 설정하면 되지" 하고 대충 넘어갔었는데, 오늘은 브라우저가 왜 이걸 막는지 제대로 들여다봤다.

same-origin policy가 기본값

브라우저는 기본적으로 스크립트가 자신과 다른 출처(origin)의 리소스를 읽지 못하게 막는다. origin은 프로토콜, 호스트, 포트 세 가지가 모두 같아야 동일하다고 판단한다. 이 정책이 없으면 내가 열어둔 은행 사이트 탭의 쿠키를 아무 사이트에서나 fetch로 훔쳐볼 수 있다.

서버가 허가증을 내주는 방식

교차 출처 요청 자체가 막히는 건 아니다. 요청은 실제로 서버까지 도달하고, 브라우저가 응답 헤더를 검사해서 스크립트에 넘겨줘도 되는지 판단한다. 서버가 Access-Control-Allow-Origin 헤더로 허용 출처를 명시해야 그때 응답을 읽을 수 있다.

preflight, 사전 확인 요청

PUT 메서드나 커스텀 헤더처럼 "단순 요청" 범위를 벗어나면 브라우저는 실제 요청 전에 OPTIONS 메서드로 preflight 요청을 먼저 보낸다. 서버가 이 예비 질문에 허용 응답을 줘야만 진짜 요청이 나간다.

정리하면 CORS는 서버를 보호하는 장치가 아니라, 브라우저가 사용자를 보호하려고 응답을 읽기 전에 거치는 검문소다. 에러를 만나면 요청이 실패한 게 아니라 응답을 막힌 것이니, 서버 쪽 헤더부터 확인하면 된다.
